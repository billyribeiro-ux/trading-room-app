## The short answer

**v4 is retired, at every layer.** It exists in exactly one place in this entire repository: a
commented-out `<p>` in the reference's Manage Room template. It never renders, so it is absent from
every DOM capture, from the decoded field table, from our schema and from our settings page — **and
it is absent from the persisted `sess` object the backend stores** (see the session-object section
below). It was not merely hidden in the UI; it was removed from the data model.

**That is not a gap. It is a match.** The reference does not render it either, and our absence of it
is the correct reproduction.

## What v4 brings to the table

**Nothing, functionally.** There is no v4 code path, no v4 setting in any live surface, and no
captured value for it anywhere.

What it brings is **information**:

1. **The version line is v3 → v4 → v5, and v4 was retired.** The template kept the row rather than
   deleting it, which tells you v4 was real at some point and was withdrawn — not that it never
   existed. The wording of the warning ("If PTR did not clear you for v4!!") is identical in form to
   v3's and v5's, so it was operated the same way.
2. **It confirms how these switches are meant to be read.** v3, v4 and v5 are peers: per-room,
   server-persisted, gated on the account being "cleared", and warned about in identical language.
   None of them is a client feature flag.
3. **It is a deliberate divergence trap.** A future reader diffing the reference template against our
   schema will find `useV4` present there and absent here and may "fix" it by adding the field. That
   would ship a control the reference does not render. Hence this file.

## Should we reproduce it? — SUPERSEDED

**The evidence-only answer was no.** The commented-out row produces no DOM node and no behaviour, so
reproducing it would ship a control the reference does not render.

**The owner has overruled that, and is right to** — see the directive at the top. We are not only
reproducing the reference here; we are choosing a version to run. v4 becomes a real setting and the
default.

So the divergence is now intentional and documented, which is the difference between a divergence and
a defect. `dont-touch-block.test.ts` pins the block's contents, so **its ordering assertions must be
updated deliberately** when the v4 row lands — and checked that they assert the full ordered list
rather than mere presence, since only the former would catch an accidental insertion.

## Honest gaps

1. **What v4 was.** Nothing in this repository says. Same gap as v5's, and for the same reason: these
   are server-side switches and the server code was not read in this pass.
2. **When and why it was retired.** Not recoverable from a static template — it would need the
   reference's own version control, which we do not have.
3. **Whether the server still accepts `useV4`.** `services/**` was not read. If a room somewhere
   still has the flag set, only the backend knows.

## The persisted session object — read 2026-08-12

The capture enumerates the actual `sess` object the backend stores
(`apps/controller/docs/reference/parts/02-baseline-720-1439.md:740-744`, duplicated at
`apps/controller/docs/reference/ptr1-DECODE.md:1916`). The version fields sit here, verbatim:

```text
customEnterDisclosure, customUserInfoURL, stAppScheduleID, invalidTokens, ssoHost, useV3, useV5,
clusterID, backupClusterID, superClusterID, superClusterExpectedServerCount, useFFmpegRecording,
useLessBusyVsRoundRobin, useMediaMTX, mediaMTXClusterID, backupMediaMTXClustterID, media_max_bitrate,
media_fir_rate, hasYTStreaming, media_relays, isLocked, chatServerURL, force_jpeg_screenshare,
force_mp3_audio, node_media_relays, node_ws_media_relays, altCodeVendorJS, altCodeAppJS
```

Three things this settles:

1. **`useV3` and `useV5` are real persisted fields** on the session record — not UI-only state.
2. **`useV4` is NOT in the object.** It was removed from the data model, not merely commented out of
   the template. So v4 is retired at the storage layer too, which is stronger than the earlier
   "commented-out markup" finding and supersedes it.
3. **`useV3, useV5` sit immediately before `clusterID`** and the entire cluster/media block that
   follows. The adjacency that the settings-page layout suggested is real in the data model as well.
   That is the strongest available evidence that these switches belong to the **media plane**, though
   it still does not say what they select.

The same note warns (`02-baseline-720-1439.md:746-748`) that the field-name typos in this list —
`disalowMultiLogins`, `styckyNonTradeAlert`, `diasableFCMAlerts`, `ingnoreBadWordsList`,
`backupMediaMTXClustterID`, `twillioApiSID`, `obsStreamSatusWebHookURL` — are **verbatim from the
capture and must be preserved by any API that talks to this backend.**

**Still not answered:** what v5 selects. The object gives the field, not its semantics.
